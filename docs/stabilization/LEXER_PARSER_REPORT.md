# Lexer and Parser Stabilization Report (Phase 02)

## Overview
This document summarizes the testing and stabilization efforts for the Viyal Lexer and Parser. A comprehensive test inventory was built against the existing grammar, and tests were added to ensure robustness against malformed input.

## Lexer Evaluation
*   **Testing:** Expanded tests cover keywords, identifiers, integers, floats, string literals (including escapes), operators, punctuation, comments, Unicode handling, and invalid characters.
*   **Robustness:** The lexer (powered by `logos`) correctly yields byte spans and recovers after encountering invalid tokens (e.g., `@`), emitting an `Err(())` for the invalid slice but continuing to the next valid token.
*   **Defects Found:**
    *   **Unicode Identifiers:** The current regex `[a-zA-Z_][a-zA-Z0-9_]*` does not support Unicode characters in identifiers (e.g., `变量`). They yield lexing errors.
    *   **String Escapes:** The lexer correctly bounds strings with `\"`, but does not unescape sequences like `\n` into actual newline characters in the AST payload. It just stores the raw matched slice.

## Parser Evaluation
*   **Testing:** Expanded tests for classes, functions, variable declarations, expressions, control flow, imports, option/result types, and match expressions.
*   **Negative Testing:** Added test cases for missing delimiters, malformed expressions, incomplete declarations, and unexpected EOFs.
*   **Robustness:** The parser uses synchronization points (`class`, `if`, `while`, `for`, `return`) to recover from syntax errors, allowing it to collect multiple errors rather than aborting immediately. No panics or unbounded recursion loops were identified on malformed inputs.
*   **Defects Found (Regression Tests Added):**
    *   **Missing Factor Precedence (`*`, `/`):** The parser entirely lacks a `parse_factor` method in its expression precedence ladder. Expressions like `1 * 2` fail to parse, throwing an `Expected ';'` error because the parser stops at `*`.
    *   **Top-Level Variables Unsupported:** The grammar does not parse `var x = 1;` at the top level. The parser assumes anything not matching `class`, `type`, `import`, or `export` is a function declaration, causing a confusing `Expected type name` error when encountering `var` at the root scope.
    *   **`final` Keyword Mismatch:** While `final` exists in the lexer, it is unused in the parser. The parser hardcodes `var` to imply immutable (`is_final = true`) and `mut` as mutable.

## Stability & Safety
*   No stack overflows or panics occur on malformed inputs. 
*   Byte spans generated by the lexer map correctly across multiline inputs, proving reliable for diagnostics (and LSP integration).
*   Invalid inputs successfully produce structured `ParseError` diagnostics instead of crashes.

## Conclusion
The frontend parsing layer is structurally stable against crashes and handles errors gracefully. However, there are significant gaps in the implemented grammar (most notably the missing `*`/`/` operator parsing and top-level variable limitations) that were documented as regression tests. In accordance with Phase 02 constraints, the grammar architecture was preserved as-is.
