# Viyal Execution Model

## 1. Virtual Machine Architecture
Viyal currently implements a stack-based bytecode virtual machine (`VM`).
- **Instructions**: The VM executes chunks of bytecodes generated by the compiler.
- **Stack**: The execution stack consists of `Value` instances (tagged unions of primitives and object handles).
- **Call Frames**: Function invocations create a `CallFrame` on the call stack tracking the current instruction pointer (`ip`), base stack slot, and executable chunk.

## 2. Concurrency and Async
- **Status**: Scaffolding only.
- The `runtime/async` and `runtime/concurrency` crates are presently empty stubs.
- Viyal executes strictly synchronously and single-threaded. There are no task/thread life-cycles, event loops, or shared state primitives implemented at this phase.
- Because execution is single-threaded, data races between Viyal threads are fundamentally impossible right now.

## 3. Error Handling and Panics
- Viyal does not support traditional try-catch block unwinding.
- **Language Level**: Errors are returned as first-class values (via the `error()` function) and type-checked as `Result<T>` or `Option<T>`. The `?` and `or` operators manage error flow via standard branching.
- **VM Level**: Catastrophic invalid operations (e.g. attempting to call a non-function, indexing an integer) yield an `InterpretResult::RuntimeError`.
- **Panics**: When the VM returns a `RuntimeError`, the REPL or CLI terminates execution gracefully and prints the error message. Rust panics are not used for normal VM operations, preserving host application stability.

## 4. Standard Library Bindings
Native functions (e.g., standard I/O) are integrated directly into the VM state using `NativeFunctionObj`. These bridges are tightly controlled through `Result<Value, String>` returns, ensuring that if a native function fails (like a failed network request), it propagates to the VM seamlessly as a runtime error.
